# Architecture and decisions

## Scope

A single-user inventory catalog, not an ecommerce system. There are no orders, suppliers, stock movements, roles, or account management. Those workflows are outside the current product scope.

## Request path

React components → typed API client → FastAPI routes → product services → SQLAlchemy session → PostgreSQL.

Routes define HTTP behavior and validated DTOs. PUT replaces the editable representation; PATCH validates and writes only explicitly supplied fields, rejecting empty patches and null required values. Services contain product queries and writes. SQLAlchemy models define persistent types and constraints. Alembic owns schema evolution.

The backend uses synchronous SQLAlchemy with psycopg. FastAPI executes synchronous route handlers in its thread pool. This avoids blocking the event loop and keeps the implementation straightforward for a small CRUD application.

## Validation and representation

Name is trimmed and required. Optional description, category, and image URL are normalized to null when blank. HTTPS image URLs are validated and stored, and rendered directly by the browser with a fallback; the server never fetches remote images. Price uses Decimal and NUMERIC(12,2), with precision validated before PostgreSQL can round it. Quantity rejects fractional values, numeric strings, and booleans. Extra request fields are rejected.

PostgreSQL checks protect against negative prices, negative quantities, blank names, and excessive description length, even when writes bypass HTTP. VARCHAR limits constrain name/category length. NOT NULL protects mandatory values.

Responses use explicit Pydantic models, not raw database objects. A decimal string avoids JSON floating-point representation in the API contract. UI currency formatting uses JavaScript Intl for display only.

## Transactions and failures

Each request gets a session. Each successful write commits once, and reads back the database-generated values. A failed request closes the session and rolls back uncommitted changes. A missing or soft-deleted record returns 404. Deletion is a conditional UPDATE of the non-null is_deleted flag, never a physical DELETE. List/count/search/statistics queries filter active records explicitly. Database exceptions are logged and returned as generic 503 responses, without connection strings or SQL details.

Concurrent edits use last-write-wins. Optimistic locking would be appropriate for a multi-user version but is outside the current product scope.

## Query design

The list endpoint runs a count query and a bounded, ordered select. It does not fetch the entire catalog to paginate or filter in Python.

A partial GIN trigram index over active rows (is_deleted IS FALSE) supports case-insensitive substring search. Input is parameterized and SQL LIKE metacharacters are escaped so a search for '%' means a literal percent sign. Very short terms may still use sequential scans; this is a PostgreSQL planner decision.

A partial composite B-tree index on created_at DESC, id DESC over active rows supports default pagination order. ID is a stable tie-breaker for products created at the same timestamp.

Stats are calculated using one aggregate query and always represent the whole inventory, independently of the current search. No extra summary table or cache needs to be synchronized.

Offset pagination is easy to inspect and sufficient for a small catalog. A much larger catalog would justify keyset pagination, search-specific query plans, and separately considered total counts.

## Schema and hosted providers

Products reference a persistent categories table through a nullable category_id foreign key. A case-insensitive unique name index prevents duplicate categories, and categories survive product reassignment and soft deletion. The API accepts/returns category names for compatibility; a joined many-to-one relationship avoids per-row category lookups. IDs are generated by PostgreSQL. created_at is a timezone-aware timestamp assigned by the database. All prices use the same documented currency, INR.

Use a direct PostgreSQL connection for Alembic on Neon/Supabase, with TLS required. The provider's database role must be allowed to enable pg_trgm, or an admin should enable it before migrations. Migrations are applied explicitly, not during every Python application startup; the optional Compose backend runs them once before starting its server.

Rolling the complete migration chain back to base removes the categories and products tables. The initial migration deliberately retains pg_trgm because it can be shared by other applications.

## Frontend behavior

TanStack Query separates list, statistics, and detail caches. Mutations refresh list/statistics and update the detail cache. The server is the source of truth; no deletion is applied before its successful API response. After confirmation, matching cached rows/counts and unchanged inventory summaries update immediately, then background revalidation restores authoritative server state. Pre-delete reads are canceled; cache snapshots prevent double subtraction if a newer response already reflects the change. Inventory-value adjustments use integer minor units (BigInt) to avoid floating-point subtraction. No browser-local persistence is used.

Search is debounced; query keys isolate results for different terms/pages. Page resets on search and is clamped after deletions. Detail/edit requests fetch current values from the detail endpoint. Invalid or failed saves keep form values. Edits compute and send only actual changes through PATCH. The category combobox filters the loaded shared registry locally with case-insensitive partial matching, so typing does not trigger additional API calls. Search text changes the association only after a choice is selected. The list has a bounded scroll area, keyboard selection, clear/no-match states, and persistent actions for No category and Custom category. Category count is unlimited. Category and page-size controls share the same design tokens, and all confirmations share one dialog component.

Native dialogs provide modal keyboard/focus behavior. All row actions have accessible names, validation messages are associated with fields, and mutation buttons are disabled while requests are pending.

## Verification layers

1. Python DTO tests: price precision, bounds, whitespace, optional text and read-only fields.
2. PostgreSQL integration tests: actual migrations, HTTP flows, search and ordering, transactions, aggregates, database constraints.
3. Frontend unit tests: form rules and HTTP client/error handling.
4. Browser UI tests: deterministic request fixtures exercise frontend flows and responsive layout.
5. Opt-in live browser test: same UI against the real backend/database.

Fixture browser tests are not substitutes for database integration tests. GitHub CI uses an isolated PostgreSQL service. The workflow applies migrations, executes integration tests, and checks migration reversal independently of the frontend tests.
